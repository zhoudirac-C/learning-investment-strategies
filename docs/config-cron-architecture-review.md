> 日期：2026-06-08
> 触发：用户要求 review 观察池/持仓池设计 + Hermes cron 定时任务
> 目标：实现 UP 式的全局市场观 + 持仓操作建议

## 二、现状缺陷

### 缺陷1：Cron任务冗余

当前9个盘中分析任务（09:26 / 09:45 / 10:00 / 10:30 / 11:00 / 11:20 / 13:10 / 14:00 / 14:55），实际只有 ~4-5 个有独立价值。其余是同一套prompt在不同时间跑，LLM自己根据时间判断重点——脆弱且不可靠。

**更根本的问题**：每个cron任务是**独立的**。10:30不知道09:45说了什么，14:00不知道上午发生了什么。UP的全局观是连续的——"早上看修复 → 中午说修复弱了 → 下午清仓"——这个**观点演进链**在系统中完全断裂。

### 缺陷2：Watchlist膨胀失控（3718行）

- 大量票的 `technical_narrative.trend` 停留在"6月1日"，永不过期
- UP提过一次的票永久留在池子里，没有生命周期管理
- 没有优先级过滤——100+只票，今天该看哪10只？
- 缺少从"关注→可买→持仓→清仓"的状态流转

### 缺陷3：Claims → 操作全手动链路

每次新增claims后需要手动跑6-7步：
```
新claims → 判断影响哪些票 → 更新watchlist narrative → 
更新strategy_pack entry_points → 调整positions → 
discover → Neo4j → Qdrant → 重启Agent
```

一天多篇UP内容就要跑多轮，效率低且容易遗漏。

### 缺陷4：持仓池缺乏状态桥接

`entry_points` 里写了介入区间（如"亨通光电 82-85介入"），但如果真的到了82——**谁告诉我？哪个cron负责检查？**

entry_points 只是文档，不是触发器。缺乏自动化的"条件单"机制。

### 缺陷5：复盘与盘中割裂

收盘复盘（15:20 cron）给的建议**不会自动反馈到第二天的策略中**。需要手动读复盘报告 → 手动修改 strategy_pack → 手动调整。

## 三、成熟方案：引入状态机中间层

### 核心思路

UP的炒股方法论本质是一个**状态机**：

```
观察市场 → 判断阶段 → 确定方向优先级 → 
筛选标的 → 等待条件触发 → 执行 → 复盘
```

当前系统缺少的是**Layer 1（状态机层）**——一个持久化的全局状态，让所有cron任务、Agent、量化规则共享同一个"现在在哪"的认知。

### 建议架构

```
┌─────────────────────────────────────────────┐
│  Layer 0: 数据层（已有 ✅）                     │
│  claims → Neo4j/Qdrant → 607条结构化知识       │
├─────────────────────────────────────────────┤
│  Layer 1: 状态机层（🔴 缺失）                   │
│  daily_state.json:                            │
│    - market_stage: 调整末期/情绪拐点/主升...    │
│    - direction_priority: [燃气轮机🔥🔥🔥,      │
│      光纤🔥🔥, AI材料🔥, 昇腾⚠️]               │
│    - position_stance: 进攻/防御/空仓           │
│    - active_entry_conditions: [               │
│      万泽回踩31→加仓, 亨通到82→观察...]        │
├─────────────────────────────────────────────┤
│  Layer 2: 事件驱动层（精简 cron）               │
│  09:30 开盘 briefing（基于状态机+竞价数据）     │
│  14:00 午盘 check（偏离状态机预期？）           │
│  15:10 收盘 review（更新状态机+写复盘）          │
├─────────────────────────────────────────────┤
│  Layer 3: 量化触发层（已有，需增强）             │
│  stock_monitor.py 持续轮询（2-5分钟间隔）       │
│  触发条件：价格区间 / 板块偏离 / 指数破位        │
│  触发后 → 推精简告警（非完整分析）              │
└─────────────────────────────────────────────┘
```

### 改进1：精简Cron → 3个LLM节点 + 量化轮询

| 时间 | 做什么 | 用LLM？ |
|------|--------|---------|
| 09:30 | 盘前简报：竞价 + 今日 claims 要点 + 持仓状态 | ✅ |
| 盘中 | stock_monitor 持续轮询：价格触发→精简告警 | ❌ 纯规则 |
| 14:00 | 午盘偏离检查：实际走势 vs 状态机预期 | ✅ |
| 15:10 | 收盘复盘：更新状态机 + 写复盘报告 | ✅ |

原因：UP不会每30分钟发一条动态。他在**关键节点**做判断。其余时间让量化规则跑轮询。

### 改进2：daily_state.json — 全局状态机

持久化的JSON文件，记录"今天市场是什么状态"：

```json
{
  "date": "2026-06-08",
  "market_stage": "破位清仓触发，等待修复",
  "direction_priority": [
    {"direction": "燃气轮机", "intensity": "🔥🔥🔥", "source": "claim-20260604-*"},
    {"direction": "机器人", "intensity": "🔥🔥", "source": "claim-20260608-001e"}
  ],
  "position_stance": "空仓等待",
  "active_entry_conditions": [
    {"stock": "万泽股份", "trigger": "回踩30.5-31.0", "status": "未触发"},
    {"stock": "亨通光电", "trigger": "回踩82-85", "status": "未触发"}
  ],
  "key_observations": [
    "4033破位→清仓→等修复",
    "机器人接力电力→观察持续性"
  ]
}
```

**好处**：
- 每个cron任务读取这个状态，知道"现在在哪"
- 收盘复盘自动更新状态机
- 14:00午盘检查时对比"实际 vs 预期"——这就是UP做的"验证"
- Agent的 `/chat` 也能读取，给出更连贯的分析

### 改进3：Watchlist生命周期管理

给每只观察票增加 `lifecycle_stage` 字段：

```yaml
lifecycle_stage: watching        # watching → ready → position → closed
lifecycle_updated: "2026-06-08"
days_in_stage: 5
```

- `watching`：UP提过，等待条件
- `ready`：条件接近触发，重点盯
- `position`：已持仓
- `closed`：已清仓，移到历史
- `archived`：超过N天未更新且无新claims提及 → 自动降级

每天只关注 `watching + ready` 的票（预计从100+降到10-20只）。

### 改进4：Claims → Entry_Points 自动桥接

新claims添加后，脚本自动：
1. 提取 claims 中的 `related_stocks` 和方向判断
2. 匹配 watchlist 中对应的票
3. 标记"需更新 entry_points"的票
4. 生成建议的介入区间更新（基于 claim 内容 + 当前价格）

用户只需确认，不需从零写。

## 五、风险与取舍

| 方案 | 收益 | 风险/代价 |
|------|------|-----------|
| Cron 9→3 | 减少噪音、降低成本 | 盘中某些瞬间可能漏掉 |
| 引入状态机 | 连贯的全局观 | 状态更新逻辑需要持续维护 |
| Watchlist生命周期 | 聚焦真正有价值的标的 | 需要迁移现有3718行数据 |
| Claims→Entry自动化 | 减少手动操作 | 自动化可能出错，需要审核机制 |
| 量化轮询代替LLM盘中分析 | 更快、更可靠、更便宜 | 规则覆盖不到的场景会漏 |

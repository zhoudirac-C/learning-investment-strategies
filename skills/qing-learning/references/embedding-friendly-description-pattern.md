# Embedding-Friendly Description 编写模式

> 关联：`references/reasoning-pattern-matching-phase5.md`（匹配算法优化）、`references/reasoning-pattern-extraction-workflow.md`（推理模式工作流）

## 问题背景

当使用 Embedding（如 bge-small-zh-v1.5）进行语义匹配时，description 的质量直接决定匹配准确率。

**反例**（旧description）：
- `operation_strategy`: "制定具体的操作策略、仓位分配和买卖纪律。" → 20字，无触发场景
- `others`: "暂无法归入上述类别的独立分析模式。" → 17字，成了匹配黑洞
- `sector_rotation`: "分析板块轮动的质量、节奏和优先级..." → 27字，缺适用场景

**结果**：Embedding 匹配准确率 < 50%，"others"框架把任何查询都吸过去。

## 解决方案：四段式 Description

每个框架的 description 必须包含四个部分：

### 1. 触发场景（必须）

"当用户询问...时使用"

明确告诉 Embedding 模型（和 LLM）这个框架在什么场景下被触发。

```
✅ 好：当用户询问上游周期品（MLCC、PCB、存储、硅片...）的涨价逻辑、周期位置...
❌ 差：分析板块轮动的质量、节奏和优先级...
```

### 2. 典型查询示例（必须）

列出 4-6 个该框架能回答的典型问题。

```
✅ 好：典型查询：XX涨价怎么看、周期品处于什么阶段、上游材料能不能买...
❌ 差：（无示例）
```

这些示例是 Embedding 匹配的关键锚点——用户查询和示例的语义相似度直接决定匹配分数。

### 3. 核心关注点（推荐）

这个框架解决什么类型的问题，关注哪些核心变量。

```
✅ 好：核心关注价格变化、供需缺口、库存周期、扩产节奏。
```

### 4. 推理链概括（推荐）

用箭头连接框架的 4-5 个步骤，让 Embedding 理解框架的推理逻辑。

```
✅ 好：该框架通过验证涨价真实性→拆解供需驱动→对比历史周期位置→映射受益标的→判断持续性...
```

## 完整示例

### upstream_cycle（上游涨价周期分析框架）

```
当用户询问上游周期品（MLCC、PCB、存储、硅片、ABF、有色、化工、锂电材料、稀土、钢铁、煤炭等）
的涨价逻辑、周期位置、受益标的或能否介入时使用。核心关注价格变化、供需缺口、库存周期、扩产节奏。
典型查询：XX涨价怎么看、周期品处于什么阶段、上游材料能不能买、被动元件/资源品机会、周期股估值。
该框架通过验证涨价真实性→拆解供需驱动→对比历史周期位置→映射受益标的→判断持续性，
给出周期定位与操作建议。
```

### earnings_analysis（个股业绩拆解与定性分析框架）

```
当用户询问个股业绩、财报分析、业绩暴雷识别、业绩超预期、估值判断、季报年报解读时使用。
核心关注利润表、营收质量、一次性损益、主营趋势。
典型查询：XX业绩怎么样、财报怎么看、业绩超预期能追吗、怎么避雷、业绩是否符合预期、估值贵不贵。
该框架拆解财报异常项→还原主营趋势→定性风险性质→判断估值逻辑，区分一次性因素与真实经营改善。
```

## 效果对比

| 查询 | 旧description Top1 | 新description Top1 |
|------|-------------------|-------------------|
| 今天主线是什么 | mainline_identification ✅ | mainline_identification ✅ |
| 有色板块能不能买 | others ❌ | upstream_cycle ✅ |
| 市场情绪如何 | sentiment_cycle ✅ | sentiment_cycle ✅ |
| 操作策略建议 | operation_strategy ✅ | operation_strategy ✅ |
| 涨价周期判断 | upstream_cycle ✅ | upstream_cycle ✅ (0.838) |
| 美股大跌影响 | macro_transmission ✅ | macro_transmission ✅ |
| MLCC板块怎么看 | others ❌ | ai_industry_chain ❌ |

**结论**：新description将准确率从 ~50% 提升到 ~70%，但边界案例（同时命中多个框架关键词的查询）仍需要 LLM 重排序。

## 何时使用此模式

- 使用 Embedding（bge/m3e/OpenAI）进行语义检索时
- 框架数量较少（<20个）但每个框架主题范围较宽时
- 查询短（<15字）且语义边界模糊时

## 注意事项

1. **不要过度堆砌关键词**：description 不是 SEO，堆砌过多同义词会降低 Embedding 的区分度
2. **典型查询要真实**：不要编造用户不会问的问题，要从实际查询日志中提取
3. **长度控制在 100-200 字**：太短信息不足，太长稀释重点
4. **"others"框架要特别小心**：如果必须保留，description 要明确限定使用场景，不要写"其他/独立/无法归入"这类泛化描述

# Qing-Agent `/chat` 端点实时数据获取规范

> 记录 `/chat` 端点如何主动获取实时行情数据，以及 Hermes Agent 与 Qing-Agent 的交互约定。

## 背景

Qing-Agent 的 `/chat` 端点早期只依赖知识库检索（Neo4j claims + Qdrant wiki），不主动获取实时数据。用户询问个股/大盘时，Agent 只能基于历史观点回答，经常被诟病"没有数据硬猜"。

本规范定义 `/chat` 端点的实时数据注入逻辑。

## 架构

```
用户提问 → /chat 端点 → 查询类型检测 → 触发数据获取 → 组装 prompt → LLM 回复
                ↓
        ┌───────┴───────┐
        ↓               ↓
   个股/指数行情      板块领涨数据
   (stock_data.py)   (sector_data.py)
```

## 查询类型检测

`/chat` 根据关键词判断用户意图：

| 类型 | 触发关键词 | 获取的数据 |
|------|-----------|-----------|
| 市场/大盘 | 大盘、市场、行情、指数、上证、创业板、科创 | 主要指数 + 板块数据 |
| 板块 | 板块、行业、概念 | 主要指数 + 板块数据 |
| 个股分析 | 股、走势、分析、低点、高点、买入、卖出、抄底、减仓、加仓、持仓、套牢、解套、止损、止盈、目标价、支撑、压力 | 个股行情 + 大盘环境 + 90日K线 + 当日分时 |

注意：个股查询即使未提供 6 位股票代码，也应尝试通过**持仓配置**和**股票名称映射**获取行情。

## 数据源

### 个股/指数实时行情

- **主源**：腾讯财经 API `https://qt.gtimg.cn/q=`
  - 稳定、无需认证、支持批量
  - 返回 GBK 编码，`~` 分隔字段
  - 关键字段：1=名称, 2=代码, 3=最新价, 4=昨收, 5=开盘, 33=最高, 34=最低, 32=涨跌幅
- **降级源**：东方财富 push2 API
  - 当腾讯接口失败或返回数据不完整时自动切换
  - 所有返回数据标注 `source` 字段便于排查

### 历史K线

- **主源**：腾讯 `web.ifzq.gtimg.cn/appstock/app/fqkline/get`
- **降级源**：东方财富 `push2his.eastmoney.com/api/qt/stock/kline/get`
- **必须获取90日K线**，不能只看单日分时

### 当日分时

- **主源**：腾讯 `web.ifzq.gtimg.cn/appstock/app/minute/query`
- **降级源**：东方财富 `push2.eastmoney.com/api/qt/stock/trends2/get`
- 交易日必须获取当日分时数据

## 股票名称到代码映射

当用户用股票名称提问（如"中国长城"、"江海股份"）而未提供代码时，按以下优先级解析：

1. **从持仓配置读取**（`config/stock_monitor/positions.yaml`）
   - 遍历所有 account 的 positions，匹配 `name` 字段
   - 这是最高优先级，因为用户持仓的股票他最关心
2. **简化映射表 fallback**
   ```python
   name_to_code = {
       "中国长城": "000066",
       "贵州茅台": "600519",
       "比亚迪": "002594",
       "宁德时代": "300750",
   }
   ```

## Prompt 数据分层

注入 LLM prompt 时，必须明确区分数据可信度：

```
【实时行情数据】（✅ 主要分析依据）
- 个股/指数行情: ...
- 个股历史K线（近90日）: ...
- 个股当日分时: ...
- 板块数据: ...

【博主分析方法论】（仅供参考UP的分析框架和概念定义）
...

【博主历史观点卡】（⚠️ 历史观点，仅供参考，不得作为当前判断依据）
...
```

核心原则：
1. 所有判断必须基于【实时行情数据】
2. 历史观点不得作为当前判断依据
3. 禁止引用 claim ID 支持当前观点
4. 无实时数据时明确说明，不编造
5. **个股分析必须同时提供**：实时行情 + 90日K线 + 当日分时

## 分析框架约束

`/chat` 端点分析个股时，不能自由发挥，必须按博主六步框架执行：

1. **判断市场周期和情绪阶段**：基于大盘指数涨跌和量能
2. **判断所属板块是否是当前主线**：基于板块数据和个股属性
3. **判断个股地位**：核心 / 跟风 / 补涨 / 案例 / 过期
4. **检索博主历史提及**：从 claims/wiki 中提取相关观点和产业逻辑
5. **结合技术位置和资金面判断风险收益**：基于90日K线 + 当日分时 + 实时行情
6. **输出证伪条件和跟踪字段**：下一交易日需要观察的关键指标

详见 `qing-stock-analysis/references/qing-stock-framework.md`。

## 持仓关联分析

当用户提到"持仓""套牢""割肉""加仓"等操作时：

1. 读取 `config/stock_monitor/positions.yaml`
2. 提取该股票的：持仓股数、成本价、仓位比例、风控线、原计划
3. 结合实时盈亏给出**条件性建议**（格式："若X则Y"）
4. **禁止无条件买卖指令**

## Hermes Agent 交互约定

当用户向 Hermes Agent 询问 Qing-Agent 相关问题时（如"分析一下中国长城"），Hermes Agent 应**直接调用 Qing-Agent 的 `/chat` 端点**，而不是：
- ❌ 在 Hermes 内部做独立分析
- ❌ 绕过 `/chat` 直接读数据库或文件
- ❌ 先本地测试再转述结果

正确流程：
1. 确认 Qing-Agent 服务正在运行（`curl /health`）
2. 将用户原问题直接 POST 到 `http://127.0.0.1:8000/chat`
3. 将 `/chat` 返回的 `reply` 原样或精简后返回给用户
4. 如果服务异常，才考虑本地 fallback

**输出来源标注**：Qing-Agent 的回复开头必须标注 `[Qing-Agent 分析]`，以便用户区分这是 Qing-Agent 的输出还是 Hermes Agent 自己的判断。

原因：Qing-Agent 的 `/chat` 端点已经封装了实时数据获取、知识库检索、prompt 工程、风格约束等完整逻辑。Hermes 重复实现会导致数据不一致、风格偏离、历史观点误用。

## 重启与验证

修改 `main.py` 或 `stock_data.py` 后：

```bash
# 1. 找到并结束旧进程
kill $(pgrep -f "uvicorn qing_investment") 2>/dev/null

# 2. 重新启动
cd ~/learning-investment-strategies
.venv/bin/python -m uvicorn qing_investment.agent.main:app --host 127.0.0.1 --port 8000

# 3. 健康检查
curl -s http://127.0.0.1:8000/health

# 4. 功能测试
curl -s -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"今天大盘怎么样","session_id":"test"}'
```

## 常见陷阱

1. **服务未重启**：代码已更新但旧进程仍在运行，导致新逻辑不生效
2. **名称映射缺失**：用户说"分析一下江海股份"，但名称映射表中没有且未读取 positions.yaml，导致无法获取个股数据
3. **查询类型检测遗漏**：用户用新词问个股（如"套牢了怎么办"），但 `is_stock_query` 关键词未覆盖
4. **只看一天分时**：个股分析只获取当日分时，没有90日K线，无法判断趋势和支撑压力
5. **没有多源降级**：腾讯接口偶发失败时没有东方财富 fallback，导致数据缺失
6. **Prompt 中未明确标记数据来源**：LLM 可能混淆实时数据与历史观点
7. **Hermes 绕开 `/chat` 自行分析**：违反交互约定，易导致风格不一致和历史观点误用
8. **未按六步框架分析**：自由发挥导致"感觉没有学到 UP 的方法"

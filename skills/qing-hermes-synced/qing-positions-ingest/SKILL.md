# qing-positions-ingest

持仓数据摄入工作流。起点是**用户发来的券商持仓截图**（本环境无 vision_analyze 工具，图片一律 rapidocr OCR），终点是 positions.yaml 正确登记 + （可选）watchlist 监控 + 数据经行情交叉验证。

## 核心管线

```
截图 → rapidocr OCR(2x放大+坐标) → 解读持仓页布局 → 代码核实(东财searchapi+用户补充)
     → 行情交叉验证(市值=数量×现价) → positions.yaml 追加 → watchlist(可选) → validate+collect 验证
```

## 使用步骤

### Step 1: OCR 提取（带坐标，2x 放大）

```python
from rapidocr_onnxruntime import RapidOCR
import cv2
img = cv2.imread(图片路径)
img2 = cv2.resize(img, None, fx=2.0, fy=2.0, interpolation=cv2.INTER_CUBIC)
cv2.imwrite('/tmp/x_2x.jpg', img2)
result, _ = RapidOCR()('/tmp/x_2x.jpg')
# 按 (y//25, x) 排序输出带置信度
```

**置信度 < 0.97 的字段必须找用户确认，尤其成本价**。2x 放大通常提到 0.99+。

### Step 2: 解读持仓页布局（大同/华宝实测格式）

双行格式（每只持仓占 2 行），**列末归属用市值公式反推确认，不要凭直觉**：

- 第 1 行：`名称 | 当日盈亏额 | 持仓数量 | 成本价`
- 第 2 行：`市值 | 当日盈亏率 | 可用数量 | 现价`

**实测案例**：
- 大同证券：芯片设计 第1行末 1.003 / 第2行末 1.002，市值 2,004.00 → 2000×1.002=2,004 ✓ 所以 **第2行末=现价、第1行末=成本**（1.003）
- 华宝证券：列头明确标注 `市值|盈亏|持仓/可用|成本/现价`，顺钠股份 第1行末 11.853 / 第2行末 13.100，市值 11,790.00 → 900×13.1=11,790 ✓ **第2行末=现价 13.100、第1行末=成本 11.853**

结论：**两家券商一致 = 第1行末列成本价、第2行末列现价**。别把列头里的"成本/现价"当单值读——它对应两行的两个数字。

**⚠️ 大同 App 另一布局（2026-08-17 实测，单行 5 列）**：`名称 | 市值 | 本/现价 | 当日盈亏 | 个股仓位`
- "本/现价"列含两个数字：**成本在前、现价在后**；"当日盈亏"列含（盈亏额/盈亏率）两个数字
- **截图中无数量列** → 数量 = 市值 ÷ 现价 反推（验证：35,900×0.752=26,996.80 ✓）
- 再用当日盈亏额二次验证：盈亏额 = 数量×(现价−昨收)（430.80/35,900=0.012 → 昨收 0.740 ✓）
- rapidocr 排序坑：result 每项 = `[box(4点), text, conf]`，box[0]=[x,y]，排序 key 用 `r[0][0][1]`（左上点 y）；写 `r[0][1]` 会拿 text 字符串做 `//` 崩溃

### Step 3: 交叉验证公式（必须严格吻合）

- `市值 = 数量 × 现价`（例：84900 × 0.746 = 63,335.40 ✓）
- `收益率 = (现价 - 成本) / 成本`
- 三组市值全部吻合 → 成本/数量/现价归属确认；任一不符 → 重新核对列归属

### Step 4: 代码核实

- 截图只有简称（"芯片设计/科创半导/半导设备"）→ 东财 searchapi 搜全名：
  ```bash
  curl -s "https://searchapi.eastmoney.com/api/suggest/get?input=$(python3 -c 'import urllib.parse; print(urllib.parse.quote("公司名"))')&type=14&count=5"
  ```
- **中文必须 URL 编码**（裸中文 400）
- 用户补充代码时：**代码的实时现价必须与截图现价一致**，防张冠李戴
- **⚠️ 同板块多只 ETF 现价接近时，禁止只用现价匹配代码**（2026-08-18 实测教训）：
  OCR 简称"创AI" → 现价 1.238 匹配到 159246（创业板AIETF富国 1.230），
  实际用户持有的是 **159381**（创业板人工智能ETF华夏 1.235）——两现价差 <0.005，现价无法区分。
  正确做法：
  1. 先查**用户常用 ETF 池**（记忆：用户偏好 159381 等做板块暴露）+ 该账户历史持仓代码
  2. 多候选时用**涨跌幅/成交量/昨收/名称关键词**交叉辅助（159246 富国 vs 159381 华夏 = 发行公司不同）
  3. 仍不确定 → 列候选让用户确认，**不要赌**（赌错 = positions.yaml 登记错误代码，后续分析全错）

### Step 5: 行情交叉验证源（腾讯优先，东财 push2 偶发空）

```python
import subprocess, re
out = subprocess.run(['curl','-s','-m','10',f'https://qt.gtimg.cn/q={codes_csv}'],
                     capture_output=True).stdout.decode('gbk', errors='replace')
# v_sz002371="51~名称~代码~现价~昨收~..." f[1]名称 f[3]现价 f[4]昨收 f[31]涨跌额 f[32]涨跌幅 f[33]最高 f[34]最低
```

**⚠️ qt.gtimg.cn 返回 GBK 编码，必须 `.decode('gbk', errors='replace')`，UTF-8 直接 UnicodeDecodeError**。支持批量逗号分隔。东财 `push2 .../ulist.np/get` 与 `stock/get` 均偶发返回空 → 直接切腾讯。

### Step 6: 更新 positions.yaml

- 追加券商账户（保留现有账户不动），`updated_at` 改当天
- code 带后缀：`588780.SH` / `159516.SZ`；`position_rows` 读 `accounts[].name`；context 格式化读 `avg_cost`
- **positions.yaml 在 .gitignore（私有持仓），只改本地绝不入库**
- 回读 `yaml.safe_load` 验证结构

### Step 7: 加入 watchlist（用户要求"加进去"时）

- 挂对应 theme（半导体 ETF → `equipment_packaging_catchup`）
- `role: holding_etf` 区分持仓与观察；`priority: 持仓-券商名`
- watch_reason 写：数量@成本 + 登记日期 + 绑定 UP claims
- 验证链：
  ```bash
  python3 scripts/validate_watchlist.py   # 0 ❌ 0 ⚠️ 才提交
  # 确认进 poll 目标
  python3 -c "import sys; sys.path.insert(0,'src'); from qing_investment.monitor.fetchers import collect_quote_targets; from qing_investment.stock_monitor import load_monitor_config; print(collect_quote_targets(load_monitor_config('config/stock_monitor')))"
  ```
  **⚠️ collect_quote_targets 返回 dict 的 key 是 `名称(代码)` 格式（如 `顺钠股份(000533.SZ)`），不是裸代码**。
  验证持仓是否进监控时用子串匹配：`any(c in k for c in ['000533','603859'])`，
  不要用 `k.startswith(code)` 或 `code in targets`——会返回 0 条造成"持仓没进监控"的误判
  （2026-08-18 华宝更新实测：先以为 4 只持仓未接入，实际 82 个目标里都在，纯查询格式错）。

## 关键认知

- **ETF 代码（588/159/560）与股票同规则消费**：`stock_code_to_secid` 是通用 `6位.SH→1.xxx / 6位.SZ→0.xxx`，无需特殊处理
- **持仓已自动进行情监控**：`position_rows` → `collect_quote_targets`，watchlist 重复登记会被 `seen_secids` 去重——watchlist 加 ETF 的价值是 theme 分组 + linked_claims，不是行情覆盖
- 用户持仓截图常含**当日盈亏/可用数量**等冗余字段，不要写进 positions.yaml（只登记 code/name/quantity/cost）

## 坑位

1. 东财 push2 批量接口偶发返回空字符串 → 解析 JSON 崩溃；先打印原始输出判断，再切腾讯
2. OCR 把"1.003"读成"1.002"级别误差极常见 → 市值公式验证是唯一可靠纠错手段
3. 用户补充的代码与截图现价不符 → 大概率是用户记错代码或截图过期，先问再写
4. 可用数量 ≠ 持仓数量（挂单/冻结）时，positions.yaml 记**持仓总量**，可用数可备注在 watch_reason
5. **成本价会被做 T 摊低**：同一标的截图成本与旧登记不一致（如恩捷股份 55.171→53.889），**以截图为准覆盖**，并向用户说明"做 T 后需同步更新成本，否则浮盈计算失真"——不要当作 OCR 误差忽略，也不要问用户"哪个对"（截图是券商侧的实时成本，永远是最新）
   - **补充（2026-08-19 实测）**：**减仓（尤其亏损减仓）后成本可能上升**——券商摊薄成本含已实现盈亏，亏损卖出会把剩余仓位成本抬高（如 8/19 一次减仓后：芯片设计 1.023→1.030、人工智能 1.086→1.129、创AI 1.255→1.273、创新药 0.976→1.042）。与做T摊低是同一机制的两个方向，**都是合法结果，照常登记**；向用户说明"减仓摊高成本，剩余仓位浮亏显示变大是记账效应，非新增亏损"
6. **多账户叠加**：华宝+大同两个券商账户都在同一 positions.yaml，截图只覆盖其中一个账户时，**只改该账户**，其余账户持仓保留不动
7. **盘前/收盘后截图的"现价" = 昨收价**：8:55 盘前拍的持仓页，其"现价"列显示的是**昨收**而非实时价（2026-08-18 华宝截图实测：4 只全部与腾讯 f[4] 昨收一致）。行情交叉验证时对 f[4]（昨收）而非 f[3]（实时现价）；市值公式 `数量×现价` 照常用截图价验证列归属，不受影响
8. **持仓数量变化场景**：同标的截图数量/成本与旧登记不一致时（如顺钠股份 900→10000 股、成本 11.853→11.926），以截图为准整条覆盖，并向用户说明变化（加仓/减仓/做T），不用问"哪个对"
10. **成本可为负/极低（重仓做T的合法结果）**：长期做T可把成本摊到接近 0 甚至负值（2026-08-18 大同截图实测：科创半导成本 -0.373、半导设备 0.138）。**不要当 OCR 误差或数据异常拒绝**——用盈亏公式自洽验证：`盈亏额 = 数量×(现价−成本)`、`盈亏率 = (现价−成本)/成本`，两条都对上即真实（例：1700×(1.080−(−0.373))=2,470.1≈截图2,470.66 ✓；2800×(0.781−0.138)=1,800.4≈1,801.35 ✓、盈亏率 466%≈467.18% ✓）。成本异常但公式全自洽 → 照常登记，并向用户确认"做T摊薄导致"
11. **App 显示成本 ≠ 数学自洽成本（2026-08-25 华宝实测）**：券商 App"成本"列可能是份额折算前旧值（创新药ETF显示18.457、公式反推有效成本 **0.850**：100×(0.860−0.850)=+1.00 ✓ 率1.176%✓）或摊薄口径差异（恩捷显示53.889、盈亏反推 **55.899**：100×(53.67−55.899)=−222.98≈−223 ✓）。**判定标准：显示成本与盈亏额/率矛盾时，以 `cost = 现价/(1+盈亏率)` 反推值为准登记**，并向用户说明差异原因（折算未同步/摊薄口径）。vision_analyze 只能证明"App 显示这个数"，不能证明它是正确成本。
12. **ETF 代码识别终审武器：当日盈亏额反推昨收**（2026-08-25 实测）：同板块多只 ETF 现价接近时（黄金股ETF 5只候选全在1.7-2.4），用 `昨收 = 现价 + 当日盈亏额/数量` 反推（黄金股反推昨收2.2517 → 唯一锁定 517520 永赢），比现价匹配强得多。注意华宝"当日盈亏"列实际是**累计浮动盈亏**（相对成本）而非当日变动（有色 −1273.77 = 30000×(1.883−1.9254)），列头文案不可信，先验证数值语义再消费。
10. **App 显示成本可能与自身盈亏数据矛盾（2026-08-25 华宝实测）——以盈亏反推为准**：截图显示成本 53.889 但盈亏 -223.00/-3.989% 反推成本=55.899（100×(53.67−55.899)=−222.98 ✓）；显示成本 18.457（份额折算前旧值）但盈亏 +1.00/+1.176% 与成本 0.850 精确自洽。此时 vision/OCR 复读数字也没用（显示的确实是那个数），**矛盾根源是券商记账（摊薄 vs 买入成本 / 折算未同步），不是识别错误** → 用 `成本 = 现价/(1+盈亏率)` 反推并登记反推值，向用户说明。判断顺序：先验证 OCR 是否误读（局部放大重OCR/vision 复核）→ 数字确认无误则信公式不信显示。
11. **"当日盈亏"列可能实为浮动盈亏（相对成本）**：2026-08-25 华宝截图列头写"当日盈亏"，但数值 = 数量×(现价−成本) 而非 数量×(现价−昨收)（有色 -1273.77 = 30000×(1.883−1.9254)）。**不要用该列反推昨收**来匹配 ETF 代码——会得到错误昨收导致候选全部落空。ETF 代码匹配用现价精确一致 + 同板块全量扫描（东财 searchapi 搜板块关键词取全部候选 → 腾讯批量查现价 → 唯一吻合即命中；2026-08-25 实测：有色ETF→512400 南方、黄金股→517520 永赢，均现价精确一致）。
    **补充（同日实测）**：ETF 简称搜索要覆盖**全市场同类变体**——"黄金股"需搜"黄金股/黄金ETF/黄金"多轮，候选含场内全部（159315/159321/159322/159562/517400/517520 等）；只取 searchapi 前 5 条会漏掉目标（517520 永赢排在第 6+ 位）。现价精确一致是最终判据：517520=2.193 与截图完全吻合，其余候选全在 1.7-2.4 但无一吻合。
12. **vision_analyze 可作为 OCR 的数字复核手段**：本 skill 开头说"本环境无 vision_analyze 工具"已过时——当 rapidocr 局部放大仍无法区分易混数字（53.889 vs 55.889）时，用 vision_analyze 让模型逐字读数。但注意 vision 只能确认"显示的是什么数字"，**不能解决显示值与盈亏公式矛盾的问题**（那是券商记账差异，见坑位10）。
13. **平台自动附图描述可代替 OCR 一步到位（2026-08-27 实测）**：用户发持仓截图时 Hermes 消息自带逐字段图片描述（含每只标的的数量/成本/现价/市值/盈亏），无需先跑 rapidocr——直接拿描述里的数字做 Step 3 市值公式交叉验证 + 腾讯收盘价精确匹配，全通过即可登记。仅当描述缺某字段或验证不吻合时才回退 OCR/vision 复核。9/9 验证一次通过的案例：大同 3127+华宝 5892 截图更新。
14. **负成本 = 已部分止盈的摊薄成本，不是错误**：大同持仓显示 cost 为负（如 -15.855）、且盈亏率字段为 0.000%，是券商摊薄成本口径（分红/卖出覆盖本金）。登记时原样保留负数——下游消费方（如双引擎监控脚本）用 `quantity>0` 过滤持仓而非 `cost>0`；真正的已清仓标的需要从 yaml 中整条删除或 quantity 置 0，用户截图里有"查看已清仓股票"入口但通常不可见。

### Step 8: 持仓升级到操作记录格式（2026-08-27 起 positions.yaml 为增强 schema）

用户确认后把 positions.yaml 从精简格式升级为操作记录格式（参考 `config/stock_monitor/positions.example.yaml` 的字段设计）：

- **每只持仓**新增：`strategy`（hold_or_t / reduce_on_rebound / tight_stop_do_t / range_trade / core_holding_add_on_pullback 等打法标签）、`add_zone`/`reduce_zone`/`risk_zone`（具体价格区间，precision 偏好）、`today_plan`（定调→策略→风控三段式列表）
- **顶层新增**：`snapshot`（snapshot_time/source/trading_status/overall_bias + 可选 `dual_engine_analysis` 摘要块：chan_day_summary/boll_summary/cross_validation）、`strategy_summary.priority_actions`
- 账户下可挂 `closed_positions` 记录清仓历史
- ⚠️ 兼容性：监控脚本只读 `quantity`/`cost`/`code`/`name`——新字段不影响，但写入时保持这些字段名不变（positions.yaml 用 `quantity` 不是 shares）；**负成本条目保留原样**（下游用 quantity>0 过滤）
- 分析结论落 yaml 前先与最新行情比对 risk/reduce zone 是否仍有效；双引擎分析摘要写入 `snapshot.dual_engine_analysis`（不逐标的覆盖 today_plan，除非计划过期）

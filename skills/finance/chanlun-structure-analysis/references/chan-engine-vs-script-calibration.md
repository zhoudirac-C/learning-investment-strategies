# chan_engine (量化引擎) vs chan_analysis.py (skill 简化脚本) — 口径差异实证

> 2026-08-28 会话实证。两者是**不同口径**的引擎，同一份数据上结果结构性分叉——不是"谁更准"的精度差异，是**定义差异**。
> 实证方法可复用：同一份真实 K 线分别喂两套引擎，对比笔/中枢/买卖点（口径对表）。

## 一、两套引擎定位

| | chan_analysis.py (skill 脚本) | src/chan_engine (量化引擎) |
|---|---|---|
| 位置 | ~/.hermes/skills/finance/chanlun-structure-analysis/scripts/ | ~/learning-investment-strategies/src/chan_engine/ |
| 口径 | SKILL.md 7步简化算法：间隔≥3(合并后)成笔、0.9背驰阈值、裸笔三三重叠中枢 | 337 claims 验收 + 11条 ADR 仲裁：新笔(ADR-002)、段中枢(ADR-010)、77课区间 strict(ADR-001) |
| 级别 | 无（单级别一次到位） | L0线段 → L1/L2多级中枢 + backchi 区间套 |
| 依赖 | 零第三方（纯 urllib/subprocess） | chanpy（third_party vendored）；czsc 仅对照可缺省 |
| 数据 | 腾讯日线 + 新浪分钟线 + TDX 降级链 | M6 日线 akshare→baostock（**无分钟线**） |
| is_sure | 无（全部当已确认） | 全程透传（未确认笔/段带 sure=False） |

## 三、分叉根因（按重要性排序）

1. **笔口径（新笔 vs 旧笔, ADR-002）** — 最根本。chan_analysis "间隔≥3"宽松成笔 → 短笔多 → 能凑中枢；chan_engine 新笔（须有独立K线不属于顶底分型）→ 长笔 → 凑不出。决定了中枢的"原料"完全不同。
2. **中枢构造哲学（笔中枢 vs 段中枢, ADR-010）** — 决定性。chan_analysis 对裸笔三三重叠；chan_engine 先分 L0 线段，中枢挂段结构（进入/中枢/离开段角色）。**决定性证据**：即使按重叠法用 chan_engine 的笔算，6~7月也存在重叠区 [1.869, 2.155]，但段中枢哲学下不算中枢。
3. **趋势定性** — 结果性。chan_engine 把 2026-03 之后定性为下跌趋势段（含 1 类卖点），下跌趋势段内部窄震荡不算标准中枢；chan_analysis 无趋势概念，把窄震荡当中枢。

一句话：**chan_analysis 把 6~8 月窄震荡"看成中枢"，chan_engine 把它"看成下跌趋势的中继段"**。

## 四、级别概念澄清（关键认知）

- **chan_engine 的级别 = 结构递归级别**：同一根日线上 笔→线段→L1/L2 中枢 递推（课 35/84 正统口径）。backchi 的 level-1 背驰（离开段内首末同向笔比较）就是**结构内区间套/次级别确认**——它用"笔"作次级别走势代理，不需要真 60m/30m 数据。
- **skill 的级别 = 时间周期级别**：日线/60m/30m 分别跑，跨周期**人工**验证（大级别二买=次级别一买 claim-20061205-001-a）。
- 两者是**不同的级别观**，不可混谈。把 60m 中枢直接当日线"次级别中枢"用 = 级别错配（缠论大忌）。

## 五、三周期实证（512400, 2026-08-28）：加真 60m/30m 的增量价值

chan_engine 的 `RecursionEngine` 吃 bars 不看周期，**喂 60m/30m 数据直接能跑（引擎零改动）**——M6 只是数据层没做分钟线，不是引擎不支持。实证结果：

- **日线**：8月最新笔 sure=False 未确认，无中枢无买卖点（结构未定型，"哑火"）
- **60m**：中枢 [1.712,1.851]（7/20~8/11）→ 上移 [1.860,1.960]（8/11~8/19）；**1类卖点 L2 @8/11**（对应日线 8/11 顶 1.922）+ **3类买点 L1 @8/19 价1.864**
- **30m**：中枢与 60m 同区间 [1.860,1.960]；**1类买点 L1+L2 双级别共振 @8/19 价1.864**

结论：**真次级别对"操作时机"更准**（填补日线未确认区的空白——日线一笔内部，次级别已完整走完一个走势并给买卖点）；**对"结构定性"不更准**（次级别结构不能升级为日线信号）。日线定方向级别、次级别定动手位置。数据覆盖窗口坑：60m 缓存仅 260 根（~2.6月）、30m 更短（~1.4月）。

## 六、"复用 chan_engine 替换 skill 脚本"决策框架

**不能直接替换**，三个硬约束：
1. 口径断裂：历史盘面结论（防守线/反转位/仓位性质）按简化口径产出，切换后基准不一致，对"多天连续演变复盘"是断裂点
2. 分钟线缺失：M6 文档白纸黑字"分钟级数据本期仅日线"；skill 的 60m/30m 是刚需
3. 输出契约不同：chan_engine 输出 NormalizedChart 五表（fx/bi/seg/zs/bsp+is_sure），需翻译成防守线/反转位

方案（按性价比）：
- **A（推荐）**：日线 chan_engine 结构定性（L1/L2 买卖点）+ 60m/30m 独立跑作"入场确认层" + 跨周期对齐 report adapter。复刻 skill 现有用法但口径统一到 claims 版。需补三样：数据层分钟源 + 对齐层 + 翻译层。
- **B**：真·跨周期级别递归（日线笔内部用 60m 分解确认）——缠论最正统（区间套）但工作量最大，且 chan_engine 结构内区间套已覆盖大部分价值，性价比低。
- **C**：维持 skill 简化口径 + 人工跨周期（现状）。

加真次级别"更准"的三个前提（缺一不可）：①数据层补分钟源 ②**跨周期对齐层**（RecursionEngine 单输入，三周期独立跑各出一份 NormalizedChart，不会自动对齐"60m 这个中枢对应日线哪一笔"）③输出翻译层。

## 七、数据格式坑（实证踩到）

- 日线 `fetch_tencent_daily` 返回元素带 `{"date": ...}`；分钟线 `fetch_sina` 返回元素带 `{"day": ...}`（内部已归一，缓存才是新浪原始格式）。统一解析用 `(r.get('day') or r.get('date') or '')[:16]`。
- `/tmp/klines/{code}.json` 缓存是腾讯**原始响应**（`{code,msg,data}` 包 qfqday 数组，行序 date/open/close/high/low/vol）；`{code}_{N}m.json` 是新浪原始 list。直接调 `ca.fetch_*` 命中缓存即可，勿手写解析。
- chan_engine `Bar` 格式：`Bar(ts, o, h, l, c, vol)`，`ts` 递增整数即可，不认 date 字符串；vol 缺省给 0 也行（形态学不依赖量）。
- 运行 chan_engine 需 `PYTHONPATH=src:third_party/chanpy`（Chan 模块在 vendored chanpy）；czsc 未装时 adapter_czsc 测试 error 属依赖缺失，非代码问题。

# 收盘监控复盘案例库

> 本文件收集收盘监控复盘中的典型案例，用于指导后续复盘的质量判断标准和误报/漏报识别方法。

---

## 案例一：2026-06-02 安泰科技风控线盘中变更

### 现象
- 10:00:55 风控观察：安泰科技(000969.SZ) 当前价=21.7 涨跌幅=-3.6%；触及或跌破风险线 **21.5-22**
- 11:00:44 风控观察：安泰科技(000969.SZ) 当前价=21.96 涨跌幅=-2.44%；触及或跌破风险线 **21.5-22**
- 10:30:43 风控观察：安泰科技(000969.SZ) 当前价=21.84 涨跌幅=-2.98%；触及或跌破风险线 **21.5-22**
  - 此条被去重压制

### 分析
- 三条提醒的触发价格（21.7、21.96、21.84）均落在"21.5-22"区间内，风控线一致，提醒有效。
- 但复盘时发现 `positions.yaml` 中安泰科技的 `risk_zone` 在交易时段内被修改：
  - 修改前：`risk_zone: "21.5-22"`（对应上述提醒）
  - 修改后：`risk_zone: "21.00-21.50"`
- 修改发生在 11:00 之后（第二条提醒仍使用旧阈值，后续提醒使用新阈值）。

### 判断
- **提醒本身有效**：价格确实触及了当时配置的风险线。
- **但存在时序性存疑**：盘中修改风险阈值导致前后提醒标准不一致。若用户在 11:00 看到"21.5-22"的风控提醒后自行将阈值下调至"21.00-21.50"，则后续提醒标准改变，但历史提醒仍基于旧标准。
- **去重合理**：10:30 的提醒与 10:00 的提醒间隔 30 分钟，指纹相同（action|code|name|trigger 均相同），被 30 分钟去重窗口压制，合理。

### 教训
1. **交易时段内禁止修改风险阈值**。若必须修改，应在盘后统一调整，并在次日开盘前生效。
2. 复盘时发现阈值前后不一致，必须检查 `positions.yaml` 的修改时间（`stat`）。
3. 建议在 YAML 配置建议中增加纪律条款："`positions.yaml` 的 `risk_zone`/`reduce_zone` 修改时间不得落在 09:30-15:00 之间。"

## 案例二：2026-06-02 板块轮动标签语义混淆

### 现象
- 09:26:16 防御切换观察：光通信/CPO 均涨幅1.973%、红盘率1，强于 上游涨价链、液冷/散热。当前强弱差=1.679pct
- 09:45:01 防御切换观察：防御稳定线 均涨幅0.747%、红盘率1，强于 算力租赁。当前强弱差=2.192pct
- 10:00:55 防御切换观察：防御稳定线 均涨幅1.16%、红盘率1，强于 算力租赁。当前强弱差=3.65pct

### 分析
- 第一条"防御切换观察"比较的是 **光通信/CPO（offensive）** vs **上游涨价链（offensive）**、**液冷/散热（offensive）**。
- 第二、三条"防御切换观察"比较的是 **防御稳定线（defensive）** vs **算力租赁（offensive）**。
- 第一条的两组均为 offensive style，但系统输出标签为"防御切换观察"，存在**标签语义错误**。

### 判断
- 第一条实为"进攻板块内部轮动"（光通信/CPO 强于上游涨价链/液冷），非真正的"防御切换"。
- 标签错误可能导致用户误判市场风格转向防御。

### 教训
1. 复盘时必须核对触发规则中两组各自的 `style` 属性。
2. 若两组均为 offensive，应标记为"标签语义错误——实为进攻板块内部轮动，非防御切换"。
3. 建议在 `strategy_pack.yaml` 中重命名规则或修改输出标签，避免语义混淆。

## 案例三：2026-06-02 万通发展减仓区阈值

### 现象
- 09:45:01 减仓观察：万通发展(600246.SH) 当前价=15.86 涨跌幅=0.13%；进入预设减仓区 **15.5-16**
- 11:00:44 减仓观察：万通发展(600246.SH) 当前价=15.52 涨跌幅=-2.02%；进入预设减仓区 **15.5-16**

### 分析
- 15.86 和 15.52 均落在"15.5-16"区间内，减仓提醒有效。
- 但 09:45 时涨幅仅 0.13%，价格 15.86 接近区间上沿 16，此时提醒的紧迫性较低。
- 11:00 时价格 15.52 接近区间下沿 15.5，紧迫性更高。

### 判断
- **09:45 提醒存疑**：价格接近区间上沿且涨幅为正，此时触发"减仓观察"可能过于敏感。若 `reduce_zone` 设计为"接近成本区即提醒"，则合理；若设计为"跌破成本区才提醒"，则 15.86 过早。
- **11:00 提醒有效**：价格已接近区间下沿，且跌幅扩大，减仓紧迫性提升。

### 教训
1. `reduce_zone` 的区间设计应明确语义：是"接近成本即提醒"还是"跌破成本才提醒"。
2. 若语义为"跌破成本"，区间上沿应等于或略低于成本价，而非高于成本价。
3. 建议在 `positions.yaml` 中为 `reduce_zone` 增加注释说明设计意图。

## 案例四：2026-06-02 去重压制合理性

### 现象
- 10:30:43 风控观察：安泰科技(000969.SZ) 当前价=21.84 涨跌幅=-2.98%；触及或跌破风险线21.5-22
- 此条被去重压制

### 分析
- 上一条同指纹提醒为 11:00:44（实际时间顺序：10:00:55 → 10:30:43 → 11:00:44）。
- 10:30:43 与 10:00:55 间隔约 30 分钟，恰好落在 30 分钟去重窗口边缘。
- 10:30 的价格 21.84 与 10:00 的价格 21.7 变化幅度仅 0.65%，价格变化率<0.1% 且间隔<60秒 的二次过滤不适用（间隔已为 30 分钟）。

### 判断
- **去重合理**：同一指纹在 30 分钟内重复触发，且价格变化微小，去重避免信息过载。
- 但若用户希望监控"价格持续在风险线附近徘徊"的状态，30 分钟去重可能过于宽松。

### 教训
1. 对于风控类提醒，可考虑缩短去重窗口（如 15 分钟）或增加"价格变化>1% 时突破去重"的例外规则。
2. 对于板块轮动类提醒，30 分钟去重可能合适；对于持仓风控类提醒，可能需要更短窗口。

## 案例五：2026-06-03 安泰科技减仓提醒密度偏高 + 板块轮动标签语义混淆 + 指数中间档位漏报

### 现象
- 09:26:16 进攻回流观察：CPU自研链、上游涨价链、液冷/散热 均涨幅1.527%、红盘率0.6，强于 防御稳定线。当前强弱差=1.714pct
- 09:26:16 防御切换观察：光通信/CPO 均涨幅4.58%、红盘率1，强于 上游涨价链、液冷/散热。当前强弱差=2.901pct
- 09:26:16 防御切换观察：防御稳定线 均涨幅-0.187%、红盘率0.333，强于 算力租赁。当前强弱差=1.733pct
- 13:10:21 减仓观察：安泰科技(000969.SZ) 当前价=22.68 涨跌幅=3.28%；进入预设减仓区22-23
- 14:00:19 减仓观察：安泰科技(000969.SZ) 当前价=22.35 涨跌幅=1.78%；进入预设减仓区22-23
- 14:55:53 减仓观察：安泰科技(000969.SZ) 当前价=22.09 涨跌幅=0.59%；进入预设减仓区22-23
- 上证收盘4083.97（+0.22%），处于4080-4070中间档位，无指数提醒
- 被去重压制：0条

### 分析

#### 1. 安泰科技减仓提醒
- 收盘22.12（+0.73%），全天21.73-22.97。三次触发价格（22.68、22.35、22.09）均落入 `reduce_zone: 22.00-23.00`。
- 但三次提醒均未导致实际减仓动作，且尾盘从22.09回升至22.12，说明 `reduce_zone` 区间可能过宽。
- 成本24.702，当前浮亏约-11%。`reduce_zone: 22.00-23.00` 意味着在浮亏-7%至-12%区间均触发减仓，密度偏高。

#### 2. 板块轮动标签语义混淆（再次确认）
- 第一条"进攻回流"：CPU自研链（万通+9.80% vs 得润-5.01%，严重分化）+ 上游涨价链 + 液冷/散热 vs 防御稳定线。
  - CPU自研链内部严重分化，"链"概念已失真。
- 第二条"防御切换"：光通信/CPO（offensive）vs 上游涨价链（offensive）+ 液冷/散热（offensive）。
  - **两组均为offensive，标签应为"进攻轮动观察"而非"防御切换"**。
- 第三条"防御切换"：防御稳定线（defensive，涨幅-0.187%）vs 算力租赁（offensive）。
  - 防御稳定线涨幅-0.187%（实际弱于大盘），却被标记为"强于"算力租赁，**实为弱于大盘的伪信号**。

#### 3. 指数中间档位漏报
- `strategy_pack.yaml` 中 `valid_close_level=4080`，`weak_close_level=4070`。
- 收盘4083.97处于4080-4070之间的"中间档位"，按interpretation应给出"弱修复/观察"信号。
- 但 `index_rules` 仅支持 `close_below` 触发，**代码未实现中间档位的主动提醒**。

### 判断
- **安泰科技减仓提醒**：合规但密度偏高，建议收窄 `reduce_zone` 或拆分为"做T区"和"减仓区"。
- **板块轮动提醒**：第二条为标签语义错误（offensive vs offensive 输出"防御切换"）；第三条为伪信号（防御组涨幅-0.187%弱于大盘）。
- **指数提醒**：规则缺失型漏报，需增加 `close_between` 规则或中间档位 `trigger_condition`。
- **去重**：今日无压制，合理。

### 教训
1. **`reduce_zone` 设计原则**：区间不宜过宽，建议上沿接近成本回收区、下沿为实际减仓执行线。可拆分为 `t_zone`（做T区间）和 `reduce_zone`（真正减仓区）。
2. **板块轮动标签校验清单**：
   - [ ] 核对触发规则中两组各自的 `style` 属性
   - [ ] 若两组均为offensive，标记为"标签语义错误——实为进攻板块内部轮动"
   - [ ] 若防御组涨幅<0且被标记为"强于"某方向，标记为"弱于大盘的伪信号"
3. **指数规则完整性检查**：
   - [ ] `index_rules` 是否仅支持 `close_below`？
   - [ ] 中间档位（如4080-4070）是否有对应提醒规则？
   - [ ] 建议增加 `close_between` 规则或 legacy 格式兜底
4. **sector_groups 清理**：`cpu_self_development` 组包含已清仓的万通发展（600246）和ST得润（002055），两者走势严重分化，该group标签已失真，建议移除或拆分。

## 案例六：2026-06-03 用户反馈驱动的配置调整

### 背景
- 用户查看 cron 任务 `fc7d8a270d84` 生成的收盘监控复盘报告后，给出4条具体反馈。
- 用户反馈不是"泛泛而谈"，而是针对复盘报告中具体章节的明确同意/修改意见。

### 用户反馈与执行

| 反馈 | 复盘报告章节 | 用户态度 | 执行动作 |
|------|------------|---------|---------|
| 安泰科技 reduce_zone 上调 | 5.1 positions.yaml | 同意建议 | reduce_zone: 22.00-23.00 → 23.00-24.00 |
| 板块轮动规则修复 | 5.2 strategy_pack.yaml | 同意3个建议 | min_spread_pct 1.0→1.5, min_red_ratio_spread 10→15, 新增 min_duration_seconds/min_consecutive_ticks |
| sector_groups 清理 | 5.3 strategy_pack.yaml | ST得润拆出去 | 将ST得润从 cpu_self_development 移到新建的 st_watch 组（style: avoid） |
| 去重窗口/轮询频率 | 5.4 去重窗口 | 质疑机制设计 | 未立即执行，需讨论"用户已执行"状态跟踪方案 |

### 关键教训

1. **用户反馈是配置调整的第一优先级**：复盘报告中的 YAML 建议只是"建议"，用户明确同意后才执行。用户不同意或质疑的，不能擅自修改。
2. **"同意"不等于"立即执行"**：用户说"我同意"后，仍需确认具体修改内容（如上调到多少），再执行 patch。
3. **质疑需要讨论而非强制执行**：用户对去重机制的质疑（"你应该观察用户是否进行了减仓"）是一个产品设计问题，不是简单的配置调整。需要讨论实现方案后再执行。
4. **配置修改必须 git 提交**：每次修改后 `git add -A && git commit && git push`，保持配置版本可追溯。
5. **复盘报告应包含"用户反馈"章节**：在标准复盘模板中增加"用户反馈与执行"章节，记录用户对每条建议的态度和实际执行结果。

## 案例七：2026-06-03 去重机制设计——"用户已执行"状态跟踪

### 问题
- 安泰科技在4小时内触发3次减仓观察（13:10、14:00、14:55），间隔均>30分钟，没去重。
- 但用户质疑：如果13:10已经按提醒减仓了，后面两次就是多余的。
- 当前去重只基于时间和指纹，不跟踪"用户是否已执行"。

### 用户原话
> "你应该观察用户是否进行了减仓，如果用户进行了减仓，你考虑是否要需要提醒，或者说你是想提醒用户再次减仓吗？不是的话，就记录已经减仓过了不用再提醒了"

### 分析
- 当前 `dedupe_minutes=30` 只能压制30分钟内的重复提醒。
- 13:10→14:00间隔50分钟，14:00→14:55间隔55分钟，均超过30分钟，所以三次都触发了。
- 但用户的核心诉求是：**如果用户已经执行了减仓，就不应该再提醒同样的动作**。

### 可能的解决方案

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **延长去重窗口** | dedupe_minutes 从30改为120（当天只提醒一次） | 简单，无需状态跟踪 | 如果用户未执行，可能错过后续更好的减仓时机 |
| **用户反馈机制** | 提醒后用户回复"已减仓"，记录到state.json | 精准，只提醒未执行的 | 需要用户主动反馈，增加交互负担 |
| **价格变化阈值** | 同一标的同一动作，只有价格变化>1%且间隔>60分钟才再次提醒 | 兼顾密度和有效性 | 仍可能提醒多次，只是减少了 |
| **动作状态跟踪** | 在state.json中增加"已提醒待执行""已执行"状态 | 最精准 | 实现复杂，需要用户确认或自动检测（如检测持仓变化） |

### 建议
- **短期**：延长去重窗口到120分钟，或增加"价格变化<0.5%且间隔<60分钟"的二次过滤。
- **中期**：实现用户反馈机制——提醒后用户回复"已减仓"，记录状态，当天不再提醒。
- **长期**：与券商API对接，自动检测持仓变化，实现"已执行"状态的自动跟踪。

### 教训
1. **去重机制不能只考虑时间维度**，还要考虑"用户是否已执行"这一业务维度。
2. **用户反馈是最直接的产品需求来源**，比任何理论分析都更有价值。
3. **复杂方案（状态跟踪）需要逐步迭代**，先解决80%的问题（延长去重窗口），再优化剩余20%。

## 有效性判断标准速查表

| 信号类型 | 有效标准 | 存疑标准 | 误报标准 |
|---------|---------|---------|---------|
| 减仓观察 | 价格确实落入 reduce_zone | 价格接近区间边缘、涨幅为正时触发 | 价格未落入区间但触发 |
| 风控观察 | 价格确实跌破 risk_zone | 价格短暂触及后迅速收回 | 价格未触及风险线但触发 |
| 进攻回流 | 15-30 分钟内市场维持方向、核心方向同步涨、指数站稳 | 仅子链驱动、核心方向未动、时间<15分钟 | 双方均未达阈值但触发 |
| 防御切换 | 同上，且两组 style 确实为 offensive vs defensive | 两组均为 offensive 但标签为"防御切换" | 同上 |

## 漏报检查清单

- [ ] 指数：是否跌破 `trend_defense`/`weak_close_level` 但未触发？
- [ ] 指数：是否处于中间档位（如 4080-4070）且无提醒？
- [ ] 持仓：每只持仓是否配置了 `reduce_zone` 和 `risk_zone`/`risk_line`？
- [ ] 持仓：已清仓标的是否仍在 `positions` 列表中？
- [ ] 板块：`sector_groups` 成员是否与 `positions.yaml` 实际持仓一致？
- [ ] 板块：轮动阈值是否过低导致开盘诱多/尾盘伪信号？
- [ ] 去重：是否过度压制了价格快速波动时的重复提醒？
- [ ] 配置：是否在交易时段内修改了 `positions.yaml`？
